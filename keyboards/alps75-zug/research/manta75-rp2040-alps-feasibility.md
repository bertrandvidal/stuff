# Feasibility research: Manta75 fork + ai03 Alps footprints + onboard RP2040

Research for [issue #14](https://github.com/bertrandvidal/stuff/issues/14), supporting the locked-in decision from issue #10: fork the Manta75 KiCad PCB, swap MX footprints for Alps (SKCM) footprints from ai03's KiCad library, and add an onboard RP2040 (no daughterboard MCU, no Pro Micro), sized for a KBD75 V2 case.

## Verdict: Feasible with caveats

The individual technical pieces (KiCad file migration, Alps footprint availability, RP2040 reference circuitry, licensing) are all clear and low-risk. The real open question is **case/outline fit**: Manta75 ships with its own bespoke exploded-layout case and leaf-spring mounting system that is dimensionally and structurally unrelated to a KBD75 V2 (a standard tray-mount 75%/TKL-style case). Forking Manta75's PCB gives a well-organized schematic/footprint starting point and a precedent for adding a small USB-C daughterboard, but the board **outline, mounting-hole positions, and plate-mount method will need a substantial redesign** to actually fit inside a KBD75 V2 shell — this is not a drop-in swap. See "Blockers / Gotchas" below.

---

## 1. Manta75 KiCad project

- **Repository**: [github.com/mymakercorner/the_manta75](https://github.com/mymakercorner/the_manta75), owned by `mymakercorner`.
- **KiCad version used**: KiCad 5.1.5, per the README ("PCB designed with Kicad 5.1.5") and confirmed by the raw file headers:
  - `Pcb/Kicad/Manta75.kicad_pcb` → `(kicad_pcb (version 20171130) (host pcbnew "(5.1.5)-3")` — this is the legacy pre-KiCad-6 S-expression PCB format.
  - `Pcb/Kicad/Manta75.sch` → `EESchema Schematic File Version 4` — legacy (pre-`.kicad_sch`) schematic format.
  - `Pcb/Kicad/Manta75.pro` → legacy INI-style project file (pre-`.kicad_pro` JSON format).
  - Source: raw files at `https://raw.githubusercontent.com/mymakercorner/the_manta75/main/Pcb/Kicad/Manta75.{kicad_pcb,sch,pro}`.
- **File extensions present**: `.kicad_pcb`, `.sch` (legacy, not `.kicad_sch`), `.pro` (legacy, not `.kicad_pro`), `.net`, plus a local footprint library folder (`RicoKicadLibrary`), `fp-lib-table`, and `fp-info-cache`. Directory layout confirmed via `Pcb/Kicad` listing (GitHub API).
- **Last update**: repo created 2022-01-23, 3 commits total, last commit `2afa185` on **2022-03-11** ("Added gerber files for plate PCB manufacturing, added screws specification in readme"). Source: `gh api repos/mymakercorner/the_manta75/commits`.
- **Will it open cleanly in current KiCad (7/8/9)?** Yes, with a one-way conversion. Per KiCad's own docs (docs.kicad.org/8.0/en/kicad/kicad.html): "Modern versions of KiCad can open files created in earlier versions, but can only write files in the latest formats." Legacy `.pro` files "can be read and will be converted to a `.kicad_pro` file by the project manager," and "the old files will not be deleted automatically." The docs also warn: "Files created or modified by one version of KiCad cannot be opened by older versions of KiCad" — so once converted forward, there's no going back to 5.1.5, and backups are recommended before conversion. No known blocking incompatibility was found; this is standard/expected legacy-format migration, not a special risk for this project specifically. The project's `fp-lib-table` will also need to be re-pointed regardless, since we're swapping in the ai03 Alps library in place of Manta75's local `RicoKicadLibrary` MX footprints.
- **MCU / stock approach** (relevant context for section 3): Manta75 does **not** use a Pro Micro daughterboard for the MCU. Its main PCB has an **onboard ATmega32U4-MU**, soldered directly, with its own 16 MHz crystal and supporting decoupling/bypass capacitors — confirmed by grepping the schematic (`L MCU_Microchip_ATmega:ATmega32U4-MU U0`, `Crystal_16MHz`, `8.2pF` load caps, `10uF`/`0.1uF` decoupling, reset switch). What Manta75 *does* offload to a separate small board is just the **USB-C connector** itself: a "[Unified C3 daughterboard](https://github.com/ai03-2725/Unified-Daughterboard)" (ai03's community USB-C breakout standard, now hosted at the [Unified-Daughterboard org](https://github.com/Unified-Daughterboard)), wired back to the main PCB via a JST cable, secured with "4X M2x4 screws for USB daughterboard" (per README). This exists purely so a damaged USB-C connector doesn't require replacing the whole mainboard — it carries no MCU logic of its own.

## 2. ai03 Alps footprint library

Two relevant ai03 repos exist; pick the current one, not the deprecated original:

- **Original / deprecated**: [github.com/ai03-2725/MX_Alps_Hybrid](https://github.com/ai03-2725/MX_Alps_Hybrid) (footprints packaged separately as [MX_Alps_Hybrid.pretty](https://github.com/ai03-2725/MX_Alps_Hybrid.pretty)). Its README states in bold at the top: **"This library has been succeeded by the [MX_V2 Library](https://github.com/ai03-2725/MX_V2)... This library will remain available... but will not be updated or maintained. Please migrate to the new one whenever possible."** (source: `raw.githubusercontent.com/ai03-2725/MX_Alps_Hybrid/master/README.md`).
- **Current / maintained**: [github.com/ai03-2725/MX_V2](https://github.com/ai03-2725/MX_V2) — "Second generation KiCad Libraries of keyboard switch footprints," not archived, last pushed 2024-08-15 (`gh api repos/ai03-2725/MX_V2`).

**Footprint for SKCM Alps** — both libraries state the same scope, in near-identical wording:
- Old repo, library `Alps_Only.pretty`: *"Only for alps SKCM/SKCL, SKBM/SKBL, and clones with same pin structure."* Files: `ALPS-1U.kicad_mod`, `ALPS-1.25U.kicad_mod`, `ALPS-1.5U.kicad_mod`, `ALPS-1.75U.kicad_mod`, `ALPS-2U.kicad_mod` … up to `ALPS-7U.kicad_mod`, `ALPS-ISO.kicad_mod`, plus `-LED` variants and `ALPS-LEDONLY(-FLIPPED).kicad_mod`. Full listing via `gh api repos/ai03-2725/MX_Alps_Hybrid/contents/Alps_Only.pretty`.
- New/recommended repo, library **`Alps_Solderable.pretty`**: *"For alps SKCM/SKCL, SKBM/SKBL, and clones with same pin structure."* Files: **`Alps-Solderable-1U.kicad_mod`**, `Alps-Solderable-1.25U.kicad_mod`, `1.5U`, `1.75U`, `2U`, `2.25U`, `2.75U`, `3U`, `6.25U`, `6.5U`, `7U`, `ISO`, plus a `-ReversedStabilizers` variant. Full listing via `gh api repos/ai03-2725/MX_V2/contents/Alps_Solderable.pretty`.
- **Recommendation**: use `Alps_Solderable.pretty` from the `MX_V2` repo (the maintained one) — footprint name **`Alps-Solderable-1U`** (and matching sizes) for the SKCM 1U keys.
- **Notes / distinguishing from other Alps variants**: the library explicitly scopes to SKCM/SKCL/SKBM/SKBL and "clones with same pin structure" — it does **not** separately call out Matias or SKCC. Matias switches use a compatible pin pattern to Alps SKCM (Matias are Alps clones), so they'd likely also fit, but SKCC (a different, chunkier Alps variant with different pin geometry) is not covered by this footprint family and would need verification if ever mixed in. Since the project uses vintage donor **SKCM** switches specifically, this is a direct match.
- **Mount type / pin spacing**: inspected the actual footprint file `Alps_Only.pretty/ALPS-1U.kicad_mod` (legacy repo, structurally identical pad layout to the new one): two `thru_hole circle` pads, pad 1 at `(-2.5, -4)` and pad 2 at `(2.5, -4.5)` relative to center, `drill 1.47mm`. This is the classic staggered/offset SKCM 2-pin PCB-mount pattern (pins not symmetric, ~5mm apart horizontally with a ~0.5mm vertical offset) — a **solder-in, PCB-mount** footprint (no hotswap-socket variant exists for Alps in either ai03 repo; hotswap sockets are only offered for MX/Gateron/Kailh Choc-type switches in `MX_V2`). This is fine for a build using salvaged vintage SKCM switches, which are typically hand-soldered anyway.
- **License**: `MX_Alps_Hybrid` LICENSE file is **MIT**, `Copyright (c) 2017 ai03` (`raw.githubusercontent.com/ai03-2725/MX_Alps_Hybrid/master/LICENSE`). `MX_V2` carries its own LICENSE file in the repo root (not individually re-verified byte-for-byte here, but the repo is presented as the direct successor under the same author/ecosystem and is conventionally also MIT — worth a quick visual check before use, but not expected to be a blocker).

## 3. Onboard RP2040 requirements vs. Manta75's stock MCU

Manta75's stock approach (section 1) is an onboard **ATmega32U4** with its own 16 MHz crystal, decoupling network, reset switch, and (implicitly) USB running at the ATmega's native 5V logic level — no separate 3.3V regulator appears necessary for that chip. Swapping to an RP2040 changes several things concretely, per Raspberry Pi's own **"Hardware design with RP2040"** guide (datasheet doc `RP-008279-DS-2`, fetched via `datasheets.raspberrypi.com/rp2040/hardware-design-with-rp2040.pdf` → redirects to `pip-assets.raspberrypi.com/categories/814-rp2040/documents/RP-008279-DS-2-hardware-design-with-rp2040.pdf`):

- **External QSPI flash is mandatory.** The datasheet states plainly: "In order to be able to store program code which RP2040 can boot and run from, we need to use a flash memory, specifically, a quad SPI flash memory" — RP2040 has *no* internal flash. Their own minimal reference design uses a **W25Q128JVS** (128 Mbit / 16 MB) QSPI flash chip, wired directly to RP2040's dedicated QSPI pins (QSPI_SCLK/SD0-3/SS) with short traces. QMK's own docs (`docs.qmk.fm/platformdev_rp2040`) list the flash chips it supports via config defines — **W25Q080 (8 Mbit/1 MB) is the QMK default**, with `AT25SF128A`, `GD25Q64CS`, `W25X10CL`, `IS25LP080`, and a generic "03H" flash also supported; a matching second-stage bootloader must be built into the firmware image for whichever chip is chosen. A smaller/cheaper W25Q080-class part is plenty for a QMK keymap; the Pi reference design's 16 MB part is oversized for this use case.
- **12 MHz crystal.** The datasheet: RP2040 can be clocked either "by injecting a clock signal... into the XIN pin, or by using a 12 MHz crystal connected between XIN and XOUT. Using a crystal is generally simpler." Reference part: Abracon **ABM8-272-T3**, "the same 12 MHz crystal used on the Raspberry Pi Pico," 30 ppm tolerance, 10 pF load capacitance (achieved with two matched load caps to ground), plus a 1 kΩ series damping resistor tuned for 3.3 V IOVDD operation. So Manta75's existing 16 MHz AVR crystal circuit must be replaced, not reused, and its component values (crystal freq, load caps, series resistor) re-derived for RP2040/3.3V.
- **USB D+/D- routing.** No external pull-up resistors are needed on USB_DP/USB_DM (RP2040 handles this internally), but the datasheet recommends controlled, matched-impedance differential routing — on their reference 1 mm-thick board, "0.8 mm wide tracks on USB_DP and USB_DM" to hit ~90Ω differential impedance. A USB-C connector needs the standard CC1/CC2 orientation-detection pull-down resistors (5.1 kΩ each) for device-mode operation — confirmed as a design element in the `Jabooby/RP2040-PCB-Keyboard` precedent (see below), which explicitly documents "USB-C port, its orientation detection pins (CC1/CC2), and the 5.1k resistors used for USB power delivery."
- **Voltage regulation.** RP2040 has an internal LDO that steps its 3.3V IOVDD down to the 1.1V DVDD core supply on-chip (connect VREG_OUT → DVDD pins, with 1 µF caps close to VREG_IN and VREG_OUT). But something external still has to produce the 3.3V IOVDD rail from 5V USB power — the Pi reference design uses a fixed **NCP1117ST33T3G** 3.3V LDO. This is a *new* requirement Manta75's current AVR-based PCB likely doesn't need (32U4 typically runs directly off 5V USB).
- **Decoupling.** The datasheet calls for decoupling capacitors placed close to RP2040's power pins, generally one per pin pair where possible, with an explicit noted trade-off in their own design (pins 48/49 share a single cap on the top layer due to space constraints) — i.e., budget real board area for this rather than treating it as an afterthought.
- **Reference design to copy directly**: Raspberry Pi provides an official, free **"RP2040 Minimal KiCad design" ZIP** (schematic + PCB + 3D render), linked directly from the datasheet's "Minimal design example" section (the "Minimal Design with Castellated Pads" you'd know as the Pico's own module design uses the same core circuit). This is a ready-to-copy starting schematic block for the power/flash/crystal/USB subsystem.
- **Existing open-source keyboard PCBs already doing this** (precedent, all KiCad, all QMK-targeted):
  - [Jabooby/RP2040-PCB-Keyboard](https://github.com/Jabooby/RP2040-PCB-Keyboard) — an RP2040 keyboard-PCB schematic-capture writeup that **explicitly uses a JST connector "for use with a Unified Daughter Board"** — i.e., the exact same ai03 Unified-Daughterboard USB-C-breakout pattern Manta75 already uses, just paired with RP2040 instead of a 32U4. Directly relevant precedent for this fork.
  - [hlord2000/Ohmbedded-RP2040-PCB-Template](https://github.com/hlord2000/Ohmbedded-RP2040-PCB-Template) — "An RP2040-based keyboard PCB KiCAD Template Project."
  - [zli117/CyberKeeb2040](https://github.com/zli117/CyberKeeb2040) — RP2040 mechanical-keyboard hardware design in KiCad 7.
  - QMK itself has first-class RP2040 support (`docs.qmk.fm/platformdev_rp2040`), with predefined "Generic Pro Micro RP2040" and "Generic RP2040" board configs to start from.

## 4. Manta75 license

- Stated explicitly in the README under "Licensing": **Creative Commons Attribution 4.0 International (CC BY 4.0)**, with badge/link to `creativecommons.org/licenses/by/4.0/`. Quote: *"The goal is to allow anyone to use all hardware design files with the least restrictions possible. This licence will allow you to make your own Manta75 and even use the hardware design files for commercial purposes."*
- **Only restriction**: attribution to the original author. There is no non-commercial clause and no share-alike/copyleft requirement — a private, unpublished, non-commercial derivative build is unambiguously permitted, and forking/modifying the PCB (footprints, MCU) is exactly the kind of derivative use the license anticipates. Source: `raw.githubusercontent.com/mymakercorner/the_manta75/main/README.md`.
- Separately, the QMK/Vial firmware forks referenced by Manta75 (`mymakercorner/qmk_firmware`, `mymakercorner/vial-qmk`, both branch `the_manta75`) are forks of QMK/Vial-QMK and therefore inherit QMK's own (GPL-family) firmware license — not itself a blocker for a private hardware build, and orthogonal to the hardware CC BY 4.0 license, but worth knowing if firmware source is redistributed later.
- ai03's `MX_Alps_Hybrid` footprint library license is **MIT** (see section 2) — no restriction of consequence for this use.

## 5. Blockers / Gotchas

1. **Case/outline mismatch is the biggest open risk.** Manta75's own case is a bespoke two-piece CNC-aluminum design (~346 × 150 mm, 15 mm bezels, exploded arrows/nav layout, no knob) with a **bottom-mount leaf-spring plate** system tuned in Fusion 360 specifically for that case. A KBD75 V2 is a different, standard tray-mount 75%/TKL-style case (per KBDfans product listings: "tray mount... typing angle 7°... compatible with KBD75 REV2.0 PCB"). Forking Manta75's PCB does **not** hand you a KBD75V2-shaped board — the outline, screw/standoff positions, and USB cutout location will all need to be redrawn to match the actual KBD75 V2 case cutout and mounting-hole pattern (which wasn't independently pinned down to exact millimeter dimensions from freely available primary sources in this pass — KBDfans doesn't publish raw case drawings publicly; community plate files from YMDK/others exist as commercial product pages, not open CAD downloads). **Before starting the fork, get the actual KBD75 V2 plate/PCB outline (DXF/STEP) from a KBD75-compatible plate maker (e.g. YMDK) or measure a real case**, since Manta75 contributes schematic/footprint/layout know-how but not board-outline compatibility.
2. **Deprecated library trap.** `ai03-2725/MX_Alps_Hybrid` is explicitly marked deprecated in its own README ("will not be updated or maintained"). Make sure the KiCad project ends up pointing at `MX_V2`'s `Alps_Solderable.pretty`, not the old repo, to avoid basing a new design on an abandoned footprint set. The two use different footprint names (`ALPS-1U` vs `Alps-Solderable-1U`) and slightly different schematic conventions (`MX_V2`'s README says it's "intended to be used with default KiCad symbols such as `SW_Push`" rather than custom hybrid symbols), so this isn't just a drop-in swap of the file — the schematic symbols bound to switches will also need to change.
3. **No Alps hotswap option.** Both ai03 libraries only offer solder-in (PCB-mount) footprints for Alps SKCM — fine given salvaged vintage switches, but rules out hotswap sockets as a convenience feature for this particular switch family, unlike the MX side of the same library.
4. **RP2040 adds real BOM/board-area complexity vs. Manta75's stock 32U4.** Concretely new vs. Manta75 as shipped: a QSPI flash chip + its wiring, a 3.3V LDO regulator (32U4 apparently runs straight off 5V USB on Manta75, no such regulator evident in the schematic), a different (12 MHz vs 16 MHz) crystal circuit with different tuning, and controlled-impedance USB differential routing. None of these are exotic, and Raspberry Pi's free reference KiCad design plus multiple existing open-source RP2040 keyboard PCBs (including one, Jabooby's, that already integrates a Unified Daughterboard USB-C module — same pattern as Manta75) make this a well-trodden path, but it's meaningfully more circuit than what's on the current Manta75 PCB.
5. **KiCad format migration is one-way.** Converting the KiCad 5.1.5 project forward to KiCad 8/9 format is expected to work cleanly per KiCad's own docs, but is irreversible for that project copy (can't reopen the converted files in 5.1.5 again) — keep the original files as committed history/backup, which a git fork naturally provides.
6. **Supply chain**: RP2040 and W25Q-series QSPI flash are both widely available, low-risk parts (multiple precedent projects note they're on JLCPCB's basic-parts library), so no meaningful sourcing concern was found.
7. **Matias/SKCC caution**: if the project ever mixes in Matias or SKCC switches alongside vintage SKCM, verify pin compatibility individually — the ai03 footprint README only explicitly covers "SKCM/SKCL, SKBM/SKBL, and clones with same pin structure," which likely includes Matias (an Alps clone) but does not explicitly claim SKCC compatibility.
